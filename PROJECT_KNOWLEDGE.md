## 1. Глоссарий терминов

* **Etix (www.etix.com)** — целевая платформа первичной продажи билетов на концерты, фестивали и спортивные мероприятия, для которой разработан данный автоматизированный чекер.
* **Шоу / Событие (Show / Performance)** — конкретное мероприятие на Etix, определяемое URL страницы покупки и набором параметров: название, целевое количество билетов, лимит на заказ и категория билетов.
* **`target_total`** — целевое суммарное количество билетов, которое требуется набрать в корзины и подтвердить к доступности по данному шоу (например, 12 билетов).
* **`max_per_order`** — лимит билетов на один заказ / на один профиль (например, 4 билета).
* **`ticket_index`** — порядковый номер (тип / категория) билета на странице Etix. Индексация **строго 1-based**:
  * `ticket_index = 1` — первая категория билетов в списке (индекс 0 в программном массиве);
  * `ticket_index = 2` — вторая категория билетов в списке (индекс 1 в программном массиве).
  * Если `ticket_index` не задан, чекер выбирает первую доступную категорию билетов.
* **AdsPower** — специализированный антидетект-браузер, управляющий изолированными профилями с индивидуальными аппаратными цифровыми отпечатками железа (Canvas, WebGL, Audio, шрифты, ClientRects, WebRTC, OS fingerprint) и назначенными резидентскими/мобильными прокси.
* **SunBrowser** — ядро браузера на базе Chromium внутри AdsPower (в проекте используются сборки ядер 147, 149, 150, 151).
* **AdsPower Local REST API** — локальный HTTP API сервер, поднимаемый десктопным клиентом AdsPower на порту `50325` (`http://127.0.0.1:50325` или `http://local.adspower.net:50325`). Предоставляет программный интерфейс запуска/остановки браузеров, динамической смены прокси и управления профилями.
* **CDP (Chrome DevTools Protocol)** — низкоуровневый протокол управления браузером через WebSocket debugging endpoint (`ws://...`). Библиотека Playwright подключается к уже запущенным окнам AdsPower через `connect_over_cdp`.
* **Группа «Inventory Etix (DO NOT TOUCH)»** (ID: `9383903`) — целевая группа профилей в AdsPower, созданная специально для чекера. Содержит 98 профилей (12 активных и 86 резервных).
* **Активные профили (Active Profiles)** — основной пул профилей (по умолчанию 12 шт), выделенный для регулярной проверки и распределения задач.
* **Резервные профили (Reserve Profiles)** — пул профилей (80+ шт) в группе, используемый для подмены вышедших из строя или заблокированных профилей.
* **DataDome** — антибот-система, внедренная на платформе Etix. Анализирует поведение пользователя, отпечатки браузера, сетевые заголовки и IP-репутацию, выдавая слайдер-капчи либо блокировки.
* **Слайдер-капча DataDome (Slider Captcha)** — защитный интерактивный экран DataDome (*«Slide right to secure your access»* / *«Please confirm you're not a bot»*), подгружаемый как в основной DOM, так и во фреймы `geo.captcha-delivery.com`.
* **Блокировка DataDome (Blocked Page)** — жесткая блокировка страницы с текстом *«Access Temporarily Blocked»*, сигнализирующая о компрометации IP-адреса.
* **Hot-Swap (Горячая замена)** — алгоритм мгновенной подмены заблокированного/упавшего профиля на чистый свободный профиль из резерва с автоматическим назначением проверенного прокси через AdsPower API без прерывания общего цикла проверки.
* **`good_proxies.txt`** — файл локальной базы проверенных рабочих прокси, на которых сайт Etix открывается без блокировок.
* **`bad_proxies.txt`** — файл истории заблокированных прокси с указанием причины блокировки и времени.
* **Session-scoped Bad Proxy (Сессионный блэклист)** — временная пометка прокси как нерабочего **строго на время текущего цикла/сессии проверки**. Предотвращает повторное назначение проблемного IP в текущем запуске, не удаляя его из базы навсегда (так как блокировка DataDome может быть временной).
* **Staggered Pipeline (Волновой конвейер со сдвигами)** — архитектурный паттерн выполнения параллельных действий профилями с рандомизированным временным сдвигом (джиттером), имитирующий живой человеческий трафик и исключающий синхронные пиковые всплески.
* **Джиттер (Jitter)** — случайное отклонение задержки в пределах заданного диапазона (например, 600–1100 мс).
* **Readiness Barrier (Барьер готовности воркеров)** — синхронизирующий барьер: все задействованные профили обязаны успешно открыть страницу события и пройти все санитарные проверки/капчи до того, как начнется стадия выбора билетов и кликов в корзину.
* **Material-UI (MUI React v5)** — UI-фреймворк компонентов на Etix (`div[role="combobox"]`, `.MuiSelect-select`, `li[role="option"]`), заменивший классические HTML `<select>`.
* **Price Tier Dropdown (Выпадающий список цен / «Best Available»)** — селектор ценовой категории (например, `#mui-component-select-selection` с опциями *«Best Available»* / *«Лучшие из доступных»*), который присутствует на некоторых событиях Etix и должен строго игнорироваться чекером при выборе количества билетов.
* **Per-Order Limit Alert (Превышение лимита заказа)** — системное модальное предупреждение Etix (*«Sorry, the number of tickets you requested will lead to over the per order limit of X. Please view your cart to adjust the number of tickets and submit again»*), возникающее при попытке набрать билетов больше разрешенного лимита площадки.
* **Auto-Recovery Лимита Заказа** — алгоритм автоматического перехвата алерта превышения лимита, динамического извлечения реального лимита площадки $X$ через регулярное выражение, повторного выбора доступного количества $X$ и повторного нажатия «Add Tickets».
* **`Clear Shopping Cart`** — кнопка/ссылка мгновенной полной очистки корзины на Etix с подтверждением в нативном JavaScript-диалоге (`dialog.accept()`).
* **All-In Pricing** — информационная плашка на Etix (*«This venue uses All-In Pricing. The total price listed includes ticket fees and taxes»*), указывающая на включение всех сборов в отображаемую цену.
* **RunContext / Checkpoint** — механизм персистентности сессии в SQLite/JSON, позволяющий возобновлять прерванный процесс проверки без повторного прогона уже проверенных шоу.
* **`report.csv`** — итоговый отчет со статусами проверки инвентаря, сохраняемый в корне проекта (без внутренней колонки URL).
* **One-Click Installer (`setup_installer.bat`)** — автономный скрипт автоматической установки «в 1 клик» для Windows: проверяет наличие Python 3.10+, создает виртуальное окружение `venv`, устанавливает библиотеки и Chromium в локальную папку `ms-playwright/`, генерирует конфиги и создает ярлык на Рабочем столе.
* **`run_gui.vbs`** — легковесный VBScript-лаунчер, запускающий графический интерфейс чекера в скрытом режиме (`windowStyle = 0`) без открытия сопутствующего черного окна командной строки (`cmd.exe`).
* **Release Packager (`pack_release.py` / `pack_release.bat`)** — утилита сборки чистого легковесного архива дистрибутива (`release/Etix_Checker_2026.zip` ~111 КБ) для передачи клиентам.
* **Tab Sanitization (Санитария вкладок AdsPower)** — алгоритм очистки и нормализации контекста браузера AdsPower при подключении через Playwright CDP: автоматическое обнаружение и закрытие лишних/стартовых вкладок AdsPower (`start.adspower.net`, пустые вкладки восстановления) с принудительным выводом единственной рабочей вкладки на передний план (`await page.bring_to_front()`).
* **Strict Readiness Barrier (Строгий барьер готовности воркеров с retry-контуром)** — расширенный механизм синхронизации `_ensure_worker_ready_for_show()` в `EtixCheckEngine`: многоэтапная верификация (до 3 попыток) того, что 100% задействованных профилей открыли целевой URL события, вывели окно на передний план, подтвердили рендеринг селекторов билетов (`[role="combobox"]`, `select`, `.smoketest-ticket-quantity`) или кнопки `Add Tickets` перед переходом к фазе набора корзин.
* **1-Click Auto-Updater (Встроенная система обновлений в 1 клик)** — механизм автоматической проверки и безопасного обновления файлов проекта непосредственно из графического интерфейса (`gui_app.py`) через модуль `UpdateService` (`src/utils/updater.py`).
* **Protected Paths (Белый список защищенных путей)** — строгий список пользовательских файлов и папок, которые категорически запрещено перезаписывать или удалять при обновлении программы: `.env`, `data/shows.csv`, `data/good_proxies.txt`, `data/bad_proxies.txt`, `data/adspower_backup/`, `runs/`, `logs/`, `screens/`, `venv/`, `ms-playwright/`, `.git/`.
* **Fallback Hydration Wait (Защитная пауза гидратации компонентов)** — повторный поиск элементов выбора билетов с задержкой 1.5 с в `EtixCartHandler` для ожидания завершения клиентского рендеринга и гидратации React/Material-UI компонентов.
* **Checkbox-выбор событий (Checkbox Show Selection)** — механизм выборочного запуска проверки конкретных мероприятий в GUI (`ShowCardWidget` + `CTkCheckBox`). Позволяет пользователю отмечать нужные шоу галочками, отключать ненужные и запускать чекер только для выбранного подмножества событий.
* **Quick Selection Bar (Панель быстрого управления выбором)** — блок управления над списком карточек событий в GUI с кнопками `✓  Выбрать все`, `✕  Снять все` и динамическим текстовым счетчиком `Выбрано: X из Y событий`.
* **Multi-Frame Piercing Detection (Мультифреймовое пронизывающее обнаружение)** — алгоритм детекции DataDome капч и страниц блокировки в `EtixDetector` (`is_slider_captcha`, `is_blocked_page`), сканирующий не только корневой DOM документа, но и рекурсивно все вложенные фреймы (`page.frames`), включая cross-origin iframe (`geo.captcha-delivery.com`, `datadome.co`).
* **3-Phase Human Motion Kinematics (3-фазная биометрическая кинематика мыши)** — улучшенная модель движения курсора по кубической кривой Безье в `_generate_bezier_points` с разгоном (ease-in), крейсерским участком с естественным микродрожанием руки по оси $Y$ ($\pm 1-3\text{px}$) и микропаузами ($15-35\text{мс}$), торможением перед упором (ease-out), паузами реакции глаза ($180-320\text{мс}$), задержкой клика ($80-160\text{мс}$) и удержанием перед отпусканием ($180-280\text{мс}$).
* **Track Edge Alignment (Выравнивание финиша по правому краю трека)** — расчет финишной координаты перетягивания ползунка на основе точной правой границы трека: $X_{\text{end}} = \text{Track.Right} - \frac{\text{Handle.Width}}{2} - \text{jitter}(1, 3)\text{px}$ с ограничением по ширине вьюпорта, предотвращающий недотягивание ползунка до упора.
* **Post-Solve Navigation Recovery (Бесшовный возврат после капчи)** — алгоритм в `_ensure_worker_ready_for_show`, который после успешного решения слайдера проверяет текущий URL страницы и, если автоматический редирект Etix не произошел, принудительно перенаправляет воркер обратно на `show.url` с подтвержденной авторизованной сессией.
* **Multi-User Profile Concurrency (Проверка занятости профилей AdsPower)** — концепция учета совместной работы нескольких операторов на одном аккаунте AdsPower: проверка статуса занятости/открытости профилей перед стартом проверки и блокировка запуска с предупреждением при нехватке свободных профилей.
* **Dynamic Pool Size (Динамический размер пула профилей)** — отказ от жесткой привязки к фиксированному числу 12 активных профилей; поддержка любого динамического количества профилей в группе «Inventory Etix (DO NOT TOUCH)» (12, 30, 80+).
* **`blocked_profiles.txt` (`data/blocked_profiles.txt`)** — защищенный локальный файл аудита профилей AdsPower, на которых сайт Etix заблокировал доступ (DataDome «Access Temporarily Blocked» или нерешаемая капча). Содержит метку времени, имя профиля, `user_id`, прокси и причину блокировки для последующей ручной или автоматической ротации цифрового отпечатка и прокси. Защищен от перезаписи при автообновлениях (`PROTECTED_PATHS`).
* **DataDome Fast-Path Detection (Мгновенное обнаружение бана DataDome)** — протокол экспресс-проверки статуса блокировки страницы (<150 мс по `document.title` и тегам `<h1>/<h2>`) сразу после навигации, минуя длительные ожидания согласий на куки, закрытия попапов и поиска селекторов схемы зала.
* **Combined Slider Selector (`slider_union`)** — оптимизированная единая CSS-выборка всех известных вариантов разметки ползунка DataDome (`#sec-slider, .sec-slider-btn, div[role='slider']...`), выполняемая за один вызов с таймаутом 200 мс (вместо последовательного опроса 11 селекторов по 300 мс каждый), снизившая время проверки капчи с 9.9 с до 10–20 мс.
* **Tax Scheme Conflict Auto-Recovery (Автоматическое разрешение конфликта налоговых схем)** — алгоритм перехвата ошибки Etix *«You requested venue has different tax scheme with the venue in cart»* с автоматическим принятием JavaScript-диалогов подтверждения, переходом по ссылке *«Empty Shopping Cart»* для сброса зависшей корзины от прошлых проверок и возвратом браузера на целевое шоу.
* **Google reCAPTCHA v2 / Liveness & Buster Cascade (Каскад обхода Google reCAPTCHA v2)** — алгоритм прохождения капчи Google reCAPTCHA v2:
  1. Внутри диалога капчи запускается цикл повторных попыток (`max_attempts = 3`): нажатие Reload ('↺', `#recaptcha-reload-button`) $\rightarrow$ проверка закрытия диалога $\rightarrow$ клик по кнопке «человечек» (нативная кнопка Google Liveness Challenge `#recaptcha-liveness-button` / `.rc-button-liveness` либо солвер Buster `#solver-button` с динамическим тулбар-фоллбеком) $\rightarrow$ ожидание до 10 секунд. Если аудио не распознано или Google выдал ошибку, диалог не закрывается, а цикл повторяет нажатие круговой стрелочки обновления (↺) и клик по «человечку».
  2. **Мгновенный Fast-Abort при DOSCaptcha:** автоматическое распознавание `.rc-doscaptcha-body` (*«Try again later / automated queries»*), когда Google блокирует аудиовызовы для данного IP, с мгновенным выходом без холостых перезагрузок.
  3. При неудаче первого цикла выполняется 1 повторная попытка с перезагрузкой страницы.
  4. При невозможности прохождения капчи сбойный профиль фиксируется в `blocked_profiles.txt`, его браузер немедленно закрывается через AdsPower API (исключая зависание окон на экране) и заменяется по Hot-Swap из резерва группы.
* **Session Status Reset (`reset_session_statuses`)** — механизм сброса сессионных статусов воркеров (`FAILED`, `IN_USE` $\rightarrow$ `RESERVE`) перед стартом проверки и после завершения цикла, предотвращающий ложное сообщение «Недостаточно свободных профилей» при повторных запусках чекера в GUI.
* **AdsPower Pagination & Rate-Limit Backoff** — автоматическая постраничная загрузка профилей (`page_size=100`, `page=1, 2...`) для аккаунтов с большим числом профилей (186+) и автоматическая пауза с повтором (1.1 сек) при возврате ошибки API `-1 Too many request per second`.
* **Dynamic Group Switching (Динамическое переключение рабочих папок)** — механизм сквозной смены активной папки AdsPower (`group_name`) через выпадающий список GUI без необходимости перезапуска приложения с мгновенным пересчетом пула и поддержкой опции «Все группы».
* **Defense-in-Depth Cart Cleanup (Глубокая защитная очистка корзин)** — гарантированная очистка корзин всех активных воркеров, оказавшихся на странице оформления заказа, даже если итоговый счетчик `total_reserved == 0` (исключает зависание забронированных билетов).
* **Govverr/EtixChecker Repository Migration** — перенос основного репозитория проекта на аккаунт `Govverr` (`https://github.com/Govverr/EtixChecker.git`), обновление эндпоинтов автоапдейтера, установщика и спецификаций прав Fine-grained Personal Access Token (`Contents: Read and write`).
* **Windows Smart App Control (SAC / Контроль приложений Windows 11)** — встроенная система безопасности Windows 11, блокирующая выполнение непроверенных C-расширений (`.pyd` / `.dll`), не имеющих достаточной облачной репутации Microsoft (`STATUS_IMAGE_BLOCKED_BY_APPLICATION_CONTROL`). В проекте приводит к сбою импорта `_greenlet` на версиях `greenlet >= 3.5.0`, решено строгой фиксацией доверенной версии `greenlet==3.1.1`.
* **UTF-8 BOM в командных файлах (Byte Order Mark)** — 3-байтовая сигнатура `EF BB BF` в начале файла, приводящая к тому, что интерпретатор `cmd.exe` считывает строку как `я╗┐@echo off`. Это вызывает синтаксическую ошибку, оставляет эхо-режим включенным (`ECHO ON`) и выводит внутренние системные команды в окно терминала. Решено обязательным сохранением `.bat` файлов в чистом UTF-8 без BOM (`40 65 63 68`).
* **Windows User Profile Isolation (Изоляция профилей пользователей Windows)** — архитектурный принцип установки и запуска чекера на ПК с несколькими учетными записями Windows (например, основной личный и рабочий профили): полное исключение общедоступного каталога `C:\Users\Public\Desktop` и создание ярлыков исключительно в контексте активного сеанса пользователя (`(Get-CimInstance Win32_ComputerSystem).UserName` / `$env:USERPROFILE`), включая папки OneDrive Desktop.
* **`SHChangeNotify` (Сброс кэша оболочки Windows Explorer)** — вызов нативной Win32 API функции `shell32.dll::SHChangeNotify(0x08000000, 0, 0, 0)` для мгновенного сброса кэша значков проводника Windows и гарантированного отображения созданного ярлыка на Рабочем столе.
* **AdsPower Start Page (`start.adspower.net`) & `Proxy failure`** — нативная служебная веб-страница SunBrowser (`http://start.adspower.net/?id={user_id}&host=...`), открываемая AdsPower при старте браузера. При недоступности, истечении или сбое прокси страница немедленно отображает крупный баннер `Proxy failure`, заглушку IP-адреса `---.---.---.---` / `-- / --` и предупреждение поставщика сети.
* **Pre-Flight Health Check & Startup Hot-Swap (Предстартовая валидация пула воркеров)** — алгоритм валидации работоспособности профилей сразу после их запуска в `cdp_pool.initialize()`: автоматическое обнаружение `Proxy failure`, мертвого IP или сетевого сбоя на `start.adspower.net` ДО перехода к проверке мероприятий, гарантированное закрытие нерабочих окон и их подмена на чистые резервные профили из группы `Inventory Etix (DO NOT TOUCH)`.
* **`NEXT_CHAT_PROMPT.md`** — служебный файл-инструкция для бесшовного переноса контекста разработки и передачи задач в новую сессию ИИ, включенный в `.gitignore`.

## 2. Правила и бизнес-логика

### 2.1. Входные данные (`data/shows.csv`)
* Входной CSV-файл содержит строки со структурой: `name,url,target_total,max_per_order,ticket_index`.
* URL события должен начинаться с `http://` или `https://`.
* `target_total >= 1`, `max_per_order >= 1`.
* `ticket_index` строго **1-based** (1 = первая строка билетов, 2 = вторая). Если не указан — выбирается 1-я доступная.
* **Приоритет `max_per_order`:** значение `max_per_order` из `shows.csv` является строго индивидуальным для каждого шоу (например, 4 для одного события и 6 для другого) и имеет наивысший приоритет.

### 2.2. Разграничение селекторов количества билетов и селекторов цен
* На страницах Etix могут одновременно присутствовать выпадающие списки выбора ценовой категории (*«Best Available»*) и выпадающие списки количества билетов.
* **Правило:** Чекер обязан фильтровать элементы `[role='combobox']`:
  * Целевые элементы количества билетов: `.smoketest-ticket-quantity [role='combobox']` или списки с числовыми опциями `1, 2, 3...`.
  * Исключаются селекторы ценовых блоков (`#mui-component-select-selection` и опции со словами *«Best Available»*, *«Лучшие из доступных»*).

### 2.3. Автоматическое восстановление при превышении лимита (Per-Order Limit Auto-Recovery)
* Если сайт Etix возвращает ошибку *«Sorry, the number of tickets you requested will lead to over the per order limit of X»*:
  1. Чекер перехватывает текст алерта и извлекает разрешенное число билетов $X$.
  2. Обновляет эффективный лимит для данного воркера до $X$.
  3. Повторно открывает выпадающий список количества, выбирает значение $X$ и повторно нажимает «Add Tickets».

### 2.4. Динамический расчет профилей и случайная выборка
* Количество профилей рассчитывается автоматически:
  $$\text{needed\_workers} = \min\left(\left\lceil \frac{\text{target\_total}}{\text{max\_per\_order}} \right\rceil, \text{total\_active\_profiles}\right)$$
* **Правило:** Если для достижения цели требуется меньше профилей, чем доступно в пуле (например, `target_total = 12`, `max_per_order = 4` $\rightarrow$ нужно всего **3 профиля** из 12), чекер запускает ровно **3 профиля**, а не все 12.
* Выборка профилей из активного пула производится **случайным образом (`random.sample`)**, а не последовательно (1, 2, 3), для равномерного распределения нагрузки по прокси.

### 2.5. Тайминги конвейера (Staggered Pipeline) и расчет на ~45 секунд
* Полный цикл проверки одного шоу на 12 профилях оптимизирован на **~45 секунд**.
* Все параллельные действия воркеров разнесены случайными временными сдвигами:
  * **Открытие URL (Navigation):** случайный сдвиг `batch_nav_delay_ms` = **600–1100 мс** между воркерами.
  * **Пауза после выбора селектора:** `after_click_sleep_ms` = **500–900 мс** (обязательна для перерисовки внутреннего React state в MUI).
  * **Клик «Add Tickets»:** случайный сдвиг `add_sequential_delay_ms` = **1000–1800 мс** между воркерами.
  * **Удержание брони:** `delay_before_clear_carts_s` = **4.0 с** перед освобождением мест.
  * **Очистка корзин:** случайный сдвиг `clear_cart_stagger_ms` = **600–1000 мс** между воркерами.

### 2.6. Жесткие безопасные пороги задержек (`MIN_SAFE_DELAYS`)
Пользователю и графическому интерфейсу **запрещено** устанавливать задержки ниже безопасных минимальных порогов с буфером (+100 мс):
* `batch_nav_delay_ms`: минимум **350.0 мс**;
* `after_click_sleep_ms`: минимум **500.0 мс**;
* `add_sequential_delay_ms`: минимум **900.0 мс**;
* `post_add_wait_ms`: минимум **1600.0 мс**;
* `delay_before_clear_carts_s`: минимум **2.2 с**;
* `clear_cart_stagger_ms`: минимум **400.0 мс**;
* `nav_timeout`: минимум **12000.0 мс** (12 секунд).

### 2.7. 3-этапный каскад обхода DataDome Slider и блокировок
Если воркер встречает слайдер-капчу или блокировку, чекер отрабатывает 3-шаговый каскад:
1. **Шаг 1: Плавный физический Drag & Drop (кривая Безье)**
   - Поиск ползунка (`.slider-button`, `#sec-slider-btn`, iframe `geo.captcha-delivery.com`).
   - Расчет длины дорожки и генерация траектории движения мыши по кубической кривой Безье с естественным ускорением/замедлением и вертикальным дрожанием ($Y \pm 1-3\text{px}$).
   - Зажатие мыши (`mouse.down`), перемещение, отпускание (`mouse.up`) и ожидание валидации 2.5 секунды. Если сайт открылся — продолжение работы.
2. **Шаг 2: Сброс куки сессии через CDP + Новая вкладка**
   - Если слайдер не сработал: очистка куки через `context.clear_cookies()`, закрытие старой вкладки, открытие ссылки в чистой вкладке. Если сайт открылся — продолжение работы.
3. **Шаг 3: Hot-Swap (горячая замена на резервный профиль)**
   - Если блокировка осталась: упавший IP помечается в сессионный черный список (`bad_proxy`).
   - Текущий воркер закрывается. Из резерва (80+ профилей) выбирается свободный профиль.
   - Через AdsPower API (`POST /api/v1/user/update`) профилю назначается рабочий прокси из `good_proxies.txt`.
   - Запускается новый воркер по CDP и подменяет упавший в конвейере.

### 2.8. Обработка мертвого или истекшего прокси
* Таймаут навигации: **18 секунд** (`nav_timeout = 18000`). Живой прокси загружает DOM за 2–5 секунд.
* Мгновенный перехват сетевых ошибок Chrome/Playwright (`net::ERR_PROXY_CONNECTION_FAILED`, `ERR_TUNNEL_CONNECTION_FAILED`, `ERR_CONNECTION_RESET`, `ERR_CONNECTION_TIMED_OUT`, `TimeoutError`, служебные страницы `chrome-error://`).
* Чекер не падает, а сразу инициирует **Hot-Swap** на резервный профиль с чистым прокси.

### 2.9. Очистка корзины (`clear_cart`)
* Очистка выполняется по кнопке/ссылке **`Clear Shopping Cart`** в один клик.
* На Etix клик по `Clear Shopping Cart` вызывает нативный браузерный диалог подтверждения (`confirm`). Чекер обязан перехватывать и подтверждать диалог через `page.once("dialog", lambda d: asyncio.create_task(d.accept()))`.
* Очистка корзин на разных профилях разносится поочередно со сдвигом `clear_cart_stagger_ms`.

### 2.10. Статусы проверки (`report.csv`)
* `OK` — суммарно зарезервировано $\ge \text{target\_total}$.
* `ЧАСТИЧНО` — зарезервирована часть билетов ($0 < \text{reserved} < \text{target\_total}$) из-за нехватки инвентаря на событии.
* `НЕДОСТАТОЧНО` — билеты закончились во время набора или 0 билетов.
* `SOLD OUT` — на странице висит баннер/селектор полной распродажи.
* `ENDED` — продажи на мероприятие завершены.
* `BLOCKED` — блокировка DataDome (после исчерпания всех 3 этапов обхода).
* `НЕ УДАЛОСЬ` — фатальная ошибка навигации или недоступность страницы.
* В файле `report.csv` отсутствует колонка URL (колонки: `name,status,target,reserved,available_approx,details,notes`).

### 2.11. Гарантированное закрытие окон AdsPower
* В блоке `finally` метода `run()` всегда вызывается `cdp_pool.close_all()`.
* Закрываются сессии Playwright, отправляются команды `/api/v1/browser/stop` в AdsPower для каждого профиля и выполняется контрольный вызов `/api/v1/browser/active` + остановка всех оставшихся окон.

### 2.12. Стандарты разработки и безопасность
* Все зависимости устанавливаются и запускаются **строго в виртуальном окружении `venv`**.
* Категорически запрещен хардкод API-ключей, токенов, паролей и прокси-кредов.
* Запрещены заглушки, моки и комментарии вида `// TODO`.
* Все `.bat` файлы в репозитории обязаны сохраняться в **кодировке Windows CRLF (`\r\n`) без UTF-8 BOM**.

### 2.13. Строгий контроль готовности профилей (Readiness Barrier & Multi-Attempt Loop)
* При проверке события каждый выделенный воркер проходит обязательный барьер `_ensure_worker_ready_for_show(worker, show, max_retries=3)`.
* **Санитария URL:** Если URL равен `about:blank`, стартовой странице AdsPower (`start.adspower.net`) или служебной странице ошибки Chrome (`chrome-error://`) — чекер принудительно вызывает `page.goto(show.url)` и переводит вкладку на передний план (`bring_to_front()`).
* **Контроль сетевых сбоев и DataDome:** Автоматический перехват `is_bad_proxy_page`, `is_blocked_page`, `is_slider_captcha` с запуском решения слайдера, сбросом куки и Hot-Swap на чистый резервный профиль.
* **Контроль рендеринга DOM:** Ожидание появления селекторов количества билетов или кнопки `Add Tickets`. Если элементы не найдены вовремя, выполняется `page.reload` и повторная попытка проверки.
* **Синхронизация перед бронированием:** Переход к стадии набора билетов в корзины (`_staggered_add_to_cart`) разрешен **только после того, как 100% задействованных воркеров подтвердили готовность и отображение страницы шоу**.

### 2.14. Правила безопасного 1-Click обновления (Protected Files Invariant)
* Процесс обновления программы (как через Git pull, так и через распаковку архива GitHub ZIP) **строго сохраняет без изменений все пользовательские файлы и данные**:
  * `.env` (конфигурация пользователя и ключи);
  * `data/shows.csv` (пользовательский список событий);
  * `data/good_proxies.txt` и `data/bad_proxies.txt` (базы рабочих и заблокированных прокси);
  * `data/adspower_backup/` (резервные копии метаданных профилей);
  * `runs/`, `logs/`, `screens/` (чекпоинты, системные логи, скриншоты);
  * `venv/`, `ms-playwright/` (виртуальное окружение Python и бинарники браузера Playwright).
* При изменении файла зависимостей `requirements.txt` апдейтер автоматически выполняет команду `venv/Scripts/pip.exe install -r requirements.txt -q`.

### 2.15. Регламент работы с Git и внесением изменений
* Разработка новых функций и исправление багов ведется **исключительно в изолированных feature-ветках** (например, `feat/...` или `fix/...`), прямые коммиты в ветку `main` запрещены.
* **Запрещен автоматический push в удаленный репозиторий Git** — пуш выполняется только после явного подтверждения пользователя.
* Перед началом написания кода агент обязан предложить варианты реализации, описать возможные краевые сценарии и согласовать подход с пользователем.

### 2.16. Выборочная проверка мероприятий через Checkbox-выбор в GUI
* Метод `EtixCheckEngine.run(shows_csv=..., shows=None, ...)` поддерживает параметр `shows: Optional[List[Show]]`.
* При запуске из GUI (`gui_app.py`) чекер анализирует состояние `card.is_selected` для каждой карточки:
  * В проверку передаются **СТРОГО** те шоу, у которых активен чекбокс.
  * Если отмечено 0 событий, выдается предупреждающее окно `messagebox.showwarning` и запуск блокируется.
  * Расчет количества профилей (`max_needed_workers`) и инициализация `RunContext(shows)` производятся исключительно для выбранных мероприятий.
  * События без галочки пропускаются и остаются в интерфейсе нетронутыми в статусе `PENDING`.
  * При снятии отметки карточка события визуально приглушается (`fg_color="#0e1424"`), а показатели дашборда (`stat_shows` и `stat_reserved`) мгновенно пересчитываются.

### 2.17. Строгая изоляция пула и Hot-Swap внутри группы «Inventory Etix (DO NOT TOUCH)»
* В группе «Inventory Etix (DO NOT TOUCH)» находится динамический пул профилей (не ограничивается 12 профилями, может пополняться до 30, 80, 100+ профилей с проверенными чистыми прокси).
* **Случайный выбор:** При запуске проверки события, требующего $N$ профилей, чекер **всегда** выбирает $N$ профилей случайным образом (`random.sample`) из всей группы `Inventory Etix (DO NOT TOUCH)` для предотвращения быстрого «выгорания» первых по списку прокси.
* **Строгий Hot-Swap:** При сбое прокси или блокировке воркера (Шаг 3 восстановления) новый профиль для подмены выбирается **СТРОГО и ИСКЛЮЧИТЕЛЬНО** из свободных профилей группы `Inventory Etix (DO NOT TOUCH)`. Запрещено брать профили из других групп AdsPower.

### 2.18. Многопользовательский режим AdsPower и детекция занятых профилей (Concurrency Check)
* На одном аккаунте AdsPower могут параллельно работать несколько операторов/пользователей.
* Перед запуском воркеров чекер должен проверять статус занятости профилей (открыт ли профиль другим процессом в AdsPower через `/api/v1/browser/active`).
* Если профиль уже занят сторонним пользователем, он исключается из выборки.
* Если в целевой группе недостаточно свободных профилей для выполнения проверки с требуемым распараллеливанием, чекер обязан предупредить пользователя и не начинать проверку.

### 2.19. Точный фактический учет зарезервированных корзин и билетов
* Если в процессе проверки часть профилей сталкивается с непреодолимой капчей, блокировкой или сетевым сбоем и зависает, чекер обязан строго фиксировать **фактически зарезервированное количество билетов** (реально подтвержденные корзины).
* Запрещено выставлять статус `OK`, если суммарное число фактически удержанных билетов меньше целевого `target_total`.

### 2.20. Границы безопасных задержек в GUI и защита от некорректных таймингов
* При реализации окна пользовательской настройки таймингов конвейера пользователю запрещено устанавливать задержки ниже безопасного минимума:
  $$\text{UserDelay} \ge \text{MIN\_SAFE\_DELAYS} + \text{SafetyBuffer} \; (100\text{ms} / 0.10\text{с})$$
* Значения проверяются валидатором с блокировкой сохранения невалидных (слишком агрессивных) параметров.

### 2.21. Протокол «1-reload $\rightarrow$ закрытие $\rightarrow$ Hot-Swap» и лимит 3-swap при блокировке DataDome
* При обнаружении жесткой блокировки («Access Temporarily Blocked») или нерешаемой капчи воркер выполняет **ровно 1 попытку** быстрого сброса сессионных кук (`clear_cookies()`) и перезагрузки страницы (с таймаутом до 10 секунд).
* Если страница остается заблокированной:
  1. Профиль автоматически фиксируется как заблокированный в файле `data/blocked_profiles.txt` (время, имя профиля, user_id, прокси, причина);
  2. Браузер гарантированно закрывается через CDP (`browser.close()`) и останавливается в AdsPower Local API (`/api/v1/browser/stop`) с таймаутом 2.5 сек, освобождая рабочий стол;
  3. Для текущего слота воркера запускается процедура Hot-Swap подбора резервного профиля из группы;
  4. Лимит замен: **не более 3 замен (swaps)** на один слот воркера за проверку события. Если все 3 резерва также оказались заблокированы, воркер исключается из пула (`stop_and_remove_worker`), а чекер завершает проверку оставшимися подтвержденными воркерами;
  5. По завершении проверки в GUI отображается модальное окно с предупреждением и активируется кнопка `🚫 Заблокированные` со списком профилей, требующих ротации прокси и отпечатков.

### 2.22. Правило абсолютной неизменяемости настроек профилей (Strict Profile Immutability)
* Категорически **запрещено** изменять или перезаписывать настройки профилей AdsPower (прокси, отпечатки, юзерагенты) через API (`POST /api/v1/user/update`).
* В методе `AdsPowerClient.update_profile_proxy` установлен защитный барьер, предотвращающий отправку мутирующих запросов.
* Резервные профили группы подключаются строго со своими нативными штатными настройками AdsPower и проходят валидацию соединения (`validate_worker_connection`). Если прокси кандидата не отвечает, профиль закрывается и подбирается следующий резерв без модификации параметров в AdsPower.

### 2.23. Сброс сессионных статусов воркеров (`reset_session_statuses`)
* Для предотвращения ложной деградации пула («Недостаточно свободных профилей» при повторных запусках) в `AdsPowerProfileManager` внедрен метод `reset_session_statuses()`.
* Метод автоматически переводит все локальные профили (кроме открытых вручную сторонними процессами `BUSY_EXTERNAL`) обратно в статус `RESERVE` и очищает временные ошибки:
  * перед каждым стартом проверки;
  * при вызове `cdp_pool.close_all()`;
  * в обработчиках завершения/сбоя проверки в GUI (`check_completed`, `check_failed`).

### 2.24. Поддержка событий со схемами залов (Seating Chart / Add-Seat Component)
* На мероприятиях со схемами залов (Seating Chart) кастомный веб-компонент Etix `<add-seat>` монтирует в DOM блок вкладок jQuery UI (`div.ui-tabs`).
* Чекер использует `wait_for(state="visible", timeout=7000)` для ожидания появления вкладки «Price Level» (`a:has-text('Price Level')`), выполняет клик и дожидается отрисовки контролов билетов в панели вкладки (`wait_for_selector`), исключая ошибочные перезагрузки и ложные статусы блокировки.
* Интегрирован каскад прохождения Google reCAPTCHA v2 при отправке формы: однократное нажатие Reload ('↺') $\rightarrow$ клик по кнопке расширения Buster ('человечек') с ожиданием 10 с $\rightarrow$ при неудаче перезагрузка страницы и 1 повторная попытка добавления билетов.

### 2.25. Автоматическое разрешение конфликтов корзины (Different Tax Scheme Auto-Recovery)
* Если при навигации на шоу возникает ошибка несовместимости налоговой схемы (*«You requested venue has different tax scheme with the venue in cart... click the link of Empty Shopping Cart»*):
  1. Чекер перехватывает конфликт (`is_tax_scheme_conflict`), не инициируя ложный сброс профиля;
  2. Автоматически принимает браузерный диалог подтверждения (`dialog.accept()`);
  3. Кликает по ссылке `Empty Shopping Cart`, очищая зависшую корзину от предыдущих тестов площадок с иным налогообложением;
  4. Дожидается перехода или повторно направляет браузер на целевой URL события `show.url`.

### 2.26. Защитная очистка корзин (Defense-in-Depth Cart Cleanup)
* Даже если суммарное число подтвержденных билетов равно 0 (`total_reserved == 0`), перед финализацией и закрытием окон чекер опрашивает всех активных воркеров.
* Если воркер находится на странице корзины (`is_cart_page`), чекер принудительно выполняет процедуру `clear_cart`, исключая зависание забронированных билетов в системе продажи.

### 2.27. Правило изоляции профилей пользователей Windows (User Profile Isolation Invariant)
* При установке программы через `setup_installer.bat` **категорически запрещено** создавать ярлыки в общедоступном каталоге `C:\Users\Public\Desktop` (`CommonDesktopDirectory`), чтобы ярлык чекера не отображался в других (личных/семейных) учетных записях на том же ПК.
* Инсталлятор обязан определять активного интерактивного пользователя сеанса через WMI `(Get-CimInstance Win32_ComputerSystem).UserName` и `$env:UserName`.
* Ярлыки создаются строго по путям активного пользователя:
  1. Реестр `HKCU:\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders` (параметры `Desktop` и `{754AC886-DF64-4C36-86B5-AA80434A0373}`);
  2. Стандартный каталог `[Environment+SpecialFolder]::Desktop`;
  3. Перенаправленные папки OneDrive (`Join-Path $env:OneDrive "Desktop"`, `Join-Path $env:USERPROFILE "OneDrive\Desktop"`, `Рабочий стол`).
* После создания ярлыка вызывается Win32 API `SHChangeNotify(SHCNE_ASSOCCHANGED)` для принудительного обновления рабочего стола проводником Windows.

### 2.28. Стандарт кодировки командных файлов (No-BOM & CRLF Invariant)
* Все командные файлы (`.bat`, `.cmd`) и VBScript (`.vbs`) обязаны сохраняться строго в кодировке **UTF-8 без сигнатуры BOM** (первые байты: `40 65 63 68` $\rightarrow$ `@ech`) и с окончаниями строк **Windows CRLF (`\r\n`)**.
* При сохранении из PowerShell запрещено использовать метод `[System.IO.File]::WriteAllText(..., [System.Text.Encoding]::UTF8)` (он пишет 3-байтовый BOM `EF BB BF`). Запись должна производиться через объект `New-Object System.Text.UTF8Encoding($false)`.
* В репозитории зафиксирован файл `.gitattributes`, принудительно задающий `*.bat text eol=crlf`, `*.cmd text eol=crlf`, `*.vbs text eol=crlf`.

### 2.29. Фиксация совместимости с Windows Smart App Control (`greenlet==3.1.1`)
* В `requirements.txt` и скрипте `setup_installer.bat` версия библиотеки `greenlet` зафиксирована строго: `greenlet==3.1.1`.
* На системах Windows 11 с активной службой **Smart App Control (SAC)** новейшие бинарные колеса (`greenlet >= 3.5.0`) блокируются ядром безопасности системы с ошибкой `ImportError: DLL load failed while importing _greenlet: Политика управления приложениями заблокировала этот файл` (`STATUS_IMAGE_BLOCKED_BY_APPLICATION_CONTROL`). Версия `3.1.1` обладает подтвержденным доверенным статусом в сигнатурных базах Microsoft.

### 2.30. Синтаксис VBScript-лаунчеров и экранирование кавычек (`q = Chr(34)`)
* В файле `run_gui.vbs` и его генераторе в `setup_installer.bat` запрещено использовать сложные цепочки экранированных кавычек (`""""`), вызывающие фатальную ошибку Windows Script Host `800A0409` («Незавершенная строковая константа»).
* Кавычки для путей формируются через переменную `q = Chr(34)` внутри verbatim here-string `@'...'@`:
  `shell.Run q & pythonwExe & q & " " & q & guiScript & q, 0, False`.
* Для исключения сбоя файловых ассоциаций (когда файлы `.vbs` открываются в «Блокноте») ярлыки на рабочем столе запускают `wscript.exe` с передачей пути к `.vbs` первым аргументом.

### 2.31. Требование Pre-Flight валидации прокси при открытии пула (Startup Health Check Requirement)
* Если чекер при запуске открывает пул профилей, и на части из них прокси не работают (отображается `Proxy failure` на `start.adspower.net`, заглушка `---.---.---.---`, сбой сети или блокировка DataDome), чекер **не имеет права приступать к проверке мероприятий**.
* Сбойные профили должны быть немедленно распознаны на стадии инициализации пула, зафиксированы в `data/blocked_profiles.txt` / `data/bad_proxies.txt`, закрыты в AdsPower и заменены по алгоритму Hot-Swap на чистые резервные профили из группы `Inventory Etix (DO NOT TOUCH)`.
* Проверка мероприятий начинается только тогда, когда 100% требуемых воркеров подтвердили работоспособность сети и доступность.

## 3. Архитектура и внешние сайты / сервисы / API

### 3.1. AdsPower Local REST API
* **Базовый URL:** `http://127.0.0.1:50325` (резервный: `http://local.adspower.net:50325`).
* **Эндпоинты:**
  * `GET /api/v1/status` — проверка подключения и статуса Local API.
  * `GET /api/v1/group/list` — поиск ID группы `Inventory Etix (DO NOT TOUCH)`.
  * `GET /api/v1/user/list` — постраничное получение метаданных всех профилей группы (ID, имя, прокси, серийный номер).
  * `GET /api/v1/browser/start?user_id={uid}&open_tabs=1` — запуск браузера профиля. Возвращает WebSocket endpoint отладчика: `data.ws.puppeteer` вида `ws://127.0.0.1:xxxxx/devtools/browser/yyyyy`.
  * `GET /api/v1/browser/stop?user_id={uid}` — остановка процесса браузера для профиля.
  * `GET /api/v1/browser/active` — получение списка всех запущенных в данный момент ID профилей.
  * `POST /api/v1/user/update` — формальный эндпоинт обновления прокси профиля.  
    Payload:
    ```json
    {
      "user_id": "k1fu8qmw",
      "user_proxy_config": {
        "proxy_soft": "other",
        "proxy_type": "http",
        "proxy_host": "1.2.3.4",
        "proxy_port": "8080",
        "proxy_user": "username",
        "proxy_password": "password",
        "proxy_url": ""
      }
    }
    ```
    > ⚠️ **Инвариант неизменяемости:** Метод `AdsPowerClient.update_profile_proxy` защищен программным барьером и не отправляет `POST /api/v1/user/update` для защиты от мутации боевых профилей оператора.
* **Особенности работы и лимиты Local API:**
  * **Постраничная пагинация:** эндпоинт `/api/v1/user/list` жестко ограничен размером страницы `page_size=100`. В `get_profiles_by_group` внедрен цикл пагинации (`page=1, 2, ...`), позволяющий бесшовно выгружать базы любого объема (186, 500+ профилей).
  * **Лимит частоты запросов (Rate-limit):** Local API допускает не более 1 запроса в секунду. При возврате ошибки `code: -1, msg: "Too many request per second, please check"` клиент автоматически выдерживает паузу 1.1 с и выполняет retry.
  * **Кэширование групп:** для снижения нагрузки на Local API список групп кэшируется в оперативной памяти на 30 секунд.

### 3.4. Защита DataDome (`geo.captcha-delivery.com`) и Google reCAPTCHA v2
* **Fast-Path раннее обнаружение бана:**
  * Сразу после навигации выполняется мгновенный анализ страницы (<150 мс по `document.title` и `h1/h2`). Если страница заблокирована («Access Temporarily Blocked»), чекер немедленно переходит к протоколу восстановления, пропуская холостые ожидания кук, попапов и схем залов (сокращение задержки реакции с 30 до 1.5–2 секунд).
* **Мультифреймовая детекция (Multi-Frame Piercing) и Combined Selector (`slider_union`):**
  * DataDome может изолировать экран капчи внутри кросс-доменного `iframe` (`geo.captcha-delivery.com`, `datadome.co`).
  * Сканируются все фреймы (`page.frames`). Все селекторы ползунка объединены в единый объединенный CSS-селектор `slider_union` с таймаутом 200 мс (вместо 11 последовательных селекторов), что сократило время опроса с 9.9 с до 10–20 мс.
* **Матрица селекторов слайдера (2026):**
  * Ползунок: `#sec-slider`, `.sec-slider-btn`, `div[role='slider']`, `.tc-slider-normal`, `.sliderContainer`, `#sec-slider-button`, `div[class*='slider']`.
  * Трек: `#sec-slider-track`, `.tc-slider-track`, `.sliderTrack`, `div[class*='track']`.
* **Биометрическая кинематика решения (Track Edge Alignment & 3-Phase Bezier):**
  * Координата финиша рассчитывается строго по правому краю трека:  
    $$X_{\text{end}} = \text{Track.Right} - \frac{\text{Handle.Width}}{2} - \text{jitter}(1, 3)\text{px}$$
  * Движение мыши моделируется по кубической кривой Безье с 3 фазами (разгон $\rightarrow$ крейсерская скорость с микродрожанием $Y \pm 1-3\text{px}$ и микропаузами $15-35\text{мс}$ $\rightarrow$ торможение перед упором).
  * Естественные человеческие задержки: реакция перед захватом ($180-320\text{мс}$), задержка после клика ($80-160\text{мс}$), физиологическое удержание в конце трека ($180-280\text{мс}$).
* **Верификация и бесшовный возврат (Post-Solve Recovery):**
  * Ожидание исчезновения слайдера и появления валидных куки `datadome` (до 3.5 с).
  * Если автоматический редирект на мероприятие не сработал, чекер принудительно перенаправляет страницу на `show.url`.
* **3-этапный каскад Google reCAPTCHA v2 (при наличии на форме):**
  * 1. Клик по кнопке Reload ('↺', `#recaptcha-reload-button`) в iframe капчи строго 1 раз;
  * 2. Если капча осталась активной — клик по кнопке «человечек» (нативная кнопка Google reCAPTCHA Liveness Challenge `#recaptcha-liveness-button` / `.rc-button-liveness` или Buster `#solver-button` с динамическим сканированием тулбара) с ожиданием решения 10 секунд;
  * 3. При неудаче — перезагрузка страницы и 1 повторная попытка добавления билетов; при сохранении капчи профиль временно блокируется на текущую сессию и заменяется по Hot-Swap.

### 3.5. Внешняя синхронизация прокси (GitHub Raw / Secret Gist)

### 3.8. GitHub REST API и Архитектура обновлений (`src/utils/updater.py`)
* **Официальный репозиторий проекта:** `https://github.com/Govverr/EtixChecker.git` (владелец: `Govverr`, ветка: `main`).
* **Проверка коммитов:** `GET https://api.github.com/repos/Govverr/EtixChecker/commits/main`
  * Заголовки запроса: `Accept: application/vnd.github.v3+json`, `User-Agent: EtixChecker-Updater/2026`.
  * Возвращает JSON с полями `sha` (полный хэш), `commit.message` (описание), `commit.author.name` (автор) и `commit.author.date` (ISO-дата).
  * Сравнивается с локальным состоянием через `get_local_version()`:
    * При наличии Git: выполняется `git log -1 --format=%H|%h|%s|%an|%cd`.
    * Для standalone-установок: считывается JSON-файл `.version`.
* **Загрузка архива:** `GET https://github.com/Govverr/EtixChecker/archive/refs/heads/main.zip`
  * Скачивание во временный каталог `tempfile.mkdtemp(prefix="etix_update_")`, распаковка zip-архива и рекурсивное копирование обновленных файлов в корень проекта.
  * **Белый список защищенных путей (`PROTECTED_PATHS`):** строго пропускаются `.env`, `data/shows.csv`, `data/good_proxies.txt`, `data/bad_proxies.txt`, `data/blocked_profiles.txt`, `data/adspower_backup/`, `runs/`, `logs/`, `screens/`, `venv/`, `ms-playwright/`, `.git/`.
* **Авто-обновление зависимостей:** При завершении обновления метод `_update_dependencies_if_needed()` проверяет наличие `requirements.txt` и выполняет установку через `venv/Scripts/pip.exe install -r requirements.txt -q`.
* **Нюансы авторизации GitHub PAT:**
  * При создании Fine-grained Personal Access Token по умолчанию выдается Read-only доступ. Для пуша изменений обязательны права: *Repository access* $\rightarrow$ *Only select repositories (EtixChecker)* $\rightarrow$ *Repository permissions* $\rightarrow$ *Contents: Read and write*.
  * Для классических токенов (Tokens classic) требуется флаг `[x] repo`.

### 3.9. Интеграция кнопки обновлений в GUI Dashboard (`gui_app.py`)
* **Кнопка `btn_updates`:** кнопка **`🔄  Проверить обновления`** расположена на верхней панели инструментов рядом с кнопкой `📁 Логи` в стилистике Slate-Navy & Indigo.
* **Асинхронный воркер:** Проверка запускается в отдельном `threading.Thread(target=worker, daemon=True)`, исключая блокировку главного цикла Tkinter.
* **События очереди `event_queue`:**
  * `"update_check_result"`: получает `(has_update, version_info, err)`. Если доступна новая версия — открывает модальный диалог `messagebox.askyesno` с описанием коммита и вопросом об обновлении.
  * `"update_applied"`: получает `(ok, message)` и уведомляет пользователя об успешной установке с предложением перезапустить приложение.

### 3.10. Особенности служебной страницы AdsPower `start.adspower.net`
* **URL:** `http://start.adspower.net/?id={user_id}&host={debug_host}`.
* **Поведение при сбое прокси:**
  * Если назначенный прокси недоступен или заблокирован провайдером, SunBrowser на стартовой странице отображает:
    * Заголовок / плашка: текст `Proxy failure` (селекторы `.proxy-error`, `h1/h2`).
    * Предупреждение провайдера: *«1. Please check if your network meets the proxy service provider's conditions (e.g., only for use outside mainland China). 2. If the proxy didn't passed the IP checker, please contact the proxy provider to resolve the problem.»*.
    * Поле внешнего IP: `---.---.---.---` / `-- / --`.
    * Сетевые ошибки: `net::ERR_PROXY_CONNECTION_FAILED`, `net::ERR_TUNNEL_CONNECTION_FAILED`, `ERR_TIMED_OUT`.
  * Стартовая страница служит надежным экспресс-индикатором состояния сети и прокси до отправки целевых HTTP-запросов к сайту Etix.

### 3.11. Особенности развертывания на Windows 11 и обход Smart App Control
* **Smart App Control (SAC):** В Windows 11 встроен интеллектуальный фильтр приложений, блокирующий неизвестные исполняемые библиотеки и C-расширения Python.
* **Импорт C-расширений:** При добавлении зависимостей в проект необходимо проверять совместимость бинарных wheels с Windows 11 SAC. Недавние релизы библиотек могут не иметь репутации в облаке Microsoft и приводить к сбою запуска. Фиксация `greenlet==3.1.1` предотвращает блокировку `_greenlet.cp311-win_amd64.pyd`.
* **Разрешение путей OneDrive:** В современных сборках Windows рабочий стол пользователя по умолчанию перенаправлен в облачный каталог OneDrive. Для поиска реального пути Рабочего стола используется считывание реестра `HKCU:\Software\Microsoft\Windows\CurrentVersion\Explorer\User Shell Folders` (параметры `Desktop` и `{754AC886-DF64-4C36-86B5-AA80434A0373}`).
